# Choomfie Activity — plan handoff
Full plan lives in the Waymond workspace (plans/choomfie-activity/plan.md).

## Task 2 — Voice pipeline interface (Req 1, 3)
- Done: `plugins/voice/pipeline/` — `VoiceEvent` contract (user_transcript, assistant_text, audio_chunk, speaking_start/end, emotion, tool_call, error), `VoicePipeline`, `RealtimeVoiceProvider`; `CascadedPipeline` wraps existing STT/TTS providers unchanged (`createCascadedPipeline` uses `getSTTProvider`/`getTTSProvider`); `RealtimePipeline` maps raw provider events and turns `set_emotion` tool calls into `emotion`. Fake-provider sequence tests in `pipeline.test.ts`.
- Left: manager.ts/listening.ts still call providers directly — wiring them through the pipeline is task 3 (config `voice.pipeline`). Cascaded emits one audio_chunk per reply (no sentence streaming yet).
- Surprises: no plan.md was in the repo before this task; 4 pre-existing `bun test` failures unrelated to voice.

## Task 3 — Config, budget guard and privacy (Req 2, 5, 11)
- Done: `VoiceConfig` gains `pipeline` (cascaded|realtime, default cascaded), `realtime`, `realtimeModel`, `dailyLimits` ("provider:model" → cap), `blockCloudInPrivate`; `parseVoiceConfig` validates on load and names the bad key/provider. `plugins/voice/pipeline/guard.ts`: `DailyBudget` (counter in `<dataDir>/voice-budget.json`, atomic writes, resets by local date), `selectWithBudget` (falls back to next pipeline, logs it), `checkCloudAudio` (refuses cloud in private, logs `⚠️ VOICE AUDIO SENT TO CLOUD PROVIDER`). Tests: `packages/core/test/voice-config.test.ts`, `plugins/voice/pipeline/guard.test.ts`.
- Left: manager.ts/listening.ts not yet wired to the guard/pipeline choice (do with task 4 when gemini exists). Provider name lists in config.ts duplicate the voice registries — keep in sync.
- Surprises: `daemon/rate-limit.ts` only parses SDK events; persistence pattern actually lives in `daemon/state-file.ts` (writeJsonAtomic), which is what the counter follows.

## Task 4 — Gemini Live provider (Req 4)
- Done: `plugins/voice/providers/gemini/` — `GeminiLiveProvider` (raw WebSocket to v1beta `BidiGenerateContent`, injectable socket), `discordToGemini` (48k stereo → 16k mono) / `geminiToDiscord` (24k mono → 48k stereo). Setup sends `contextWindowCompression.slidingWindow`, input/output transcription, `responseModalities: AUDIO`, tools `set_emotion` + `room_action` (poke, headpat, watch_together). Latest resumable `newHandle` kept; on `goAway` the old socket is closed and a new one opens with `sessionResumption.handle`. Tests in `live.test.ts`; live smoke test skips without `GEMINI_API_KEY` (optional `GEMINI_LIVE_MODEL`).
- Left: wire into manager.ts/listening.ts with the guard (`voice.realtime: gemini`, `voice.realtimeModel`); run the live smoke test on the user's machine; check `gemini-3.8-live` id there. Tool results for room_action must be sent back with `sendToolResult` by whoever handles the room (task 6/9).
- Surprises: RealtimePipeline already maps `set_emotion` → `emotion`, so the provider only emits raw tool calls. Audio sent while reconnecting after goAway throws "not connected" (no buffering).

## Handoff — Task 5: Emotion signal
- Done: `plugins/voice/pipeline/emotion.ts` — `EMOTIONS` (fixed 7), alias map + `normalizeEmotion`, `emotionEvent` (clamps intensity 0–1, default 1, throws on unknown), `routeEmotionToolCall` (realtime path; unknown name → `error` event), `SET_EMOTION_DECLARATION` (Gemini Live now reuses it instead of its own enum), `EmotionClassifier` + `NoopEmotionClassifier`. Cascaded: `setEmotion(name, intensity)` for the brain's tool handler and optional `classifier` option. Realtime: optional classifier on output transcripts. Tests: `emotion.test.ts`.
- Left: wiring the brain's actual MCP/ToolDef `set_emotion` to `CascadedPipeline.setEmotion` (needs the voice manager to own a pipeline); a real local classifier.
- Surprises: realtime used to pass raw names through unvalidated; now normalised, so emotion names are always one of the 7.

## Handoff — Task 6: Avatar state bus (Req 7, 9 server side, 12)
- Done: new workspace package `plugins/activity/` (`@choomfie/activity`). `server/mouth.ts` — `mouthLevels` (RMS of 48 kHz s16le stereo per 1/30 s window, gain 4, clamped 0–1). `server/bus.ts` — `startAvatarBus({ pipeline, allowlist, verifyToken, toBrain, port })` on `Bun.serve`: token from `Authorization: Bearer` or `?token=` (401 missing/invalid, 403 not allowlisted); publishes `mouth` (paced at 30 Hz, queued across chunks), `emotion`, `speaking`, `room` (from `room_action` tool calls) and `look_at` (via `bus.publish`); client `chat`/`poke`/`headpat` → `toBrain("[Activity] <@id> …")`; bad client JSON gets an `error` frame. Tests: `server/bus.test.ts`.
- Left: `verifyToken` is injected — task 7 must back it with the Discord token exchange (`/users/@me`). Wiring: start the bus where the voice manager owns a pipeline, and point `toBrain` at the worker's system-message path. Room tool results (`sendToolResult`) still unsent.
- Surprises: Bun 1.4 types need `Server<Data>` with a type argument. Browsers can't set WS headers, hence the `?token=` query param.

## Handoff — Task 7: Activity client (Req 8, 9 client)
- Done: `plugins/activity/web/` (Vite; `bun run --cwd plugins/activity web:build` / `web:dev`). `auth.ts` `signIn`: `ready` → refuse without `guildId` → `authorize` (identify, applications.commands) → POST `/api/token` → `authenticate`. `server/token.ts`: `handleTokenRequest` (the bus serves `/api/token` when given `oauth: { clientId, clientSecret }`) and `discordTokenVerifier` (`/users/@me`, backs the bus `verifyToken`). `avatar.ts`: `loadVrm` + `AvatarController` (mouth `aa` smoothed, emotion → VRM presets incl. embarrassed/thinking blends, blink every random 2–6 s, spine sway). `room.ts`: chat panel, click → `poke`, top 30 % of avatar → `headpat`, watch-together card opened via `openExternalLink`. `app.ts` `startActivity` with every dependency injected; `main.ts` real wiring + hardware-acceleration hint when WebGL fails. Tests: `web/test/render.test.ts` (mocked SDK, generated VRM, stub renderer), `web/test/room.test.ts` (happy-dom, click emits event), `server/token.test.ts`.
- Left (task 8): serve `web/dist` and `/avatar.vrm` from the bus host; client opens the bus at `/bus`; URL mappings; env `VITE_DISCORD_CLIENT_ID`; `ACTIVITY_BUS_PORT` for the Vite dev proxy (default 3001, my pick). Real WebGL drawing untested (no browser in sandbox): the render test runs three-vrm fully with a stub renderer. `look_at` accepted but not applied yet.
- Surprises: vrm-c sample models are VRM Public License, not CC0, so the test builds a tiny VRM 1.0 in memory (`web/test/sample-vrm.ts`, ours, CC0). three-vrm rejects meta licence URLs outside its accept list, so the sample's meta uses `https://vrm.dev/licenses/1.0/`. Bun runs all test files in one process, so happy-dom is used via `new Window()`, never registered globally.
